CANDIDATE  r5-12-dualslot-overwrite-address
AXES CHANGED  stream (new impl), arch, objective, batcher.  Kept: optim, target, head.

--------------------------------------------------------------------------------
1. THE OBSERVATION THAT MOTIVATES THIS
--------------------------------------------------------------------------------
I read evolve/jail_data/train_sample.jsonl (24 real training trajectories, 724 steps).
Three facts about the data are load-bearing and I checked each of them mechanically
rather than assuming them:

  (a) Every one of the 172 `mv` steps has output == "" and exit == 0.  Its rendered
      observation is therefore "cwd=/ exit=0\n" (or "cwd=/data exit=0\n") — a string that
      is IDENTICAL for every move in the corpus.  So the observation token of a move
      carries literally zero information about which file moved where.  The ONLY place
      the routing information exists, anywhere in the model's input, is the command
      token of that move.

  (b) Every argument in the corpus is an absolute path (0 relative args), and every
      cups_test read path (24/24) is string-identical to the destination of an earlier
      `mv` in the same trajectory.  So exact whole-path identity is sufficient to link
      a read to the move that wrote it; no fuzzy path matching is needed.

  (c) The command token is a frozen MEAN-POOLED sentence embedding
      (seq_worldmodel.encode_split pools over subword positions).  Mean pooling is
      permutation-invariant over subwords, so the embedding of
          mv /tmp/w/cups/g53/f149.tmp /tmp/w/cups/usr/share/misc/magic.txt.1
      and the embedding of the same command with its two arguments EXCHANGED are the
      same vector up to whatever the encoder's contextualisation leaves.  Source and
      destination are additively superposed in one 768-vector, and their two path
      strings in this corpus share long prefixes (/tmp/w/cups/...), so the residual
      that distinguishes them is tiny relative to the shared component.

Putting (a) and (c) together: with the baseline stream the model is asked to route
content through moves whose direction is close to unreadable from its input.  Both
programs I was given install machinery that presupposes readable directions — the
parent's head builds a SOURCE key and a DESTINATION key from the command embedding
through two extractors and one shared path-to-key encoder, and the r18/r22 arch builds
q_file/k_file (read query / write key) from the same command feature.  Neither program
changes the stream, so both feed that machinery a vector in which src and dst are
superposed and in which the dominant direction is the prefix/verb common mode shared by
every command in the corpus.  My claim is that this, not memory capacity, is the
binding constraint, and that it lives entirely in the axis I was assigned.

--------------------------------------------------------------------------------
2. WHAT THE MECHANISM IS (what the code does)
--------------------------------------------------------------------------------
stream/r5_dualslot_overwrite_path_coding.py rewrites each COMMAND token as a function of
that command's own string and its own standardized embedding, and nothing else.

  - A fixed coordinate map, `_coordinate_blocks()`, deterministically permutes range(768)
    from a SHAKE-256 digest of the constant b"dualslot-coordmap-v1" and carves four
    disjoint, COMMAND-INDEPENDENT blocks out of it: SRC (128 coords), DST (128 coords),
    VERB (32 coords), FLAGS (8 coords) — 296 coordinates in total, the same 296 for
    every command in every sequence.  The remaining 472 coordinates are never touched.

  - `_parse(cmd)` splits a command into (verb, src, dst, redirect, explicit_dst):
    first positional argument is src; dst is the redirection target for `> `/`>>`, or the
    last positional argument of a two-argument mv/cp/ln/install, otherwise dst = src.

  - `_balanced_code(path, ...)` maps a path string to a DENSE +/-g sign vector over the
    whole 128-wide block, with exactly 64 positive and 64 negative entries, chosen by
    sorting a SHAKE-256 digest of the string.  I verified in plain Python: the code sums
    to exactly 0, has squared norm exactly 288 for every path, and over 4950 pairs of
    distinct cups-shaped paths the mean |cosine| is 0.069 and the max is 0.34.

  - SRC and DST are generated by the SAME generator with the same tag, so one path yields
    the SAME 128-vector in whichever block it appears in.  A single linear map that reads
    the SRC block and a single linear map that reads the DST block therefore return the
    identical key for the identical path.  That is exactly the invariant the parent's
    head assumes when it initialises dst_ext = src_ext + small noise and pushes both
    through one shared path_key.

  - `code_cmds` OVERWRITES those 296 coordinates (index_copy_) instead of adding to them.
    This is the second half of the mechanism and it is not cosmetic: because the blocks
    sit at fixed coordinates, a linear functional restricted to a block sees the address
    and EXACTLY ZERO of the embedding, for every command.  Additive coding leaves the
    corpus-wide common mode of the command embedding inside the key path, and that common
    mode is the largest thing in a set of commands that all begin "cat /tmp/w/cups/".
    Near-parallel keys are what makes a delta-rule outer-product memory interfere with
    itself; overwriting removes that term by construction rather than asking cmd_proj to
    learn to null it.

  - Total code energy is identical for every command (equal-norm balanced codes plus a
    fixed empty-string pattern when an argument is absent), so token norm carries no
    information about command type and no command is systematically louder than another.
    Gains are chosen so the coded energy (626) is comparable to the surviving embedding
    energy (472 standardized unit-variance coordinates): the address is prominent without
    swamping the token.

  - `collate` calls `code_cmds`, so the collate the gate inspects and the coding the
    scoring instrument replays are the same function by construction.  Observation
    tokens, tgt, types, key_pad, cmd_mask and CUPS_LAYOUT="interleave2" are unchanged.

--------------------------------------------------------------------------------
3. WHY THIS IS NOT RESOLVING THE CHAIN FOR THE MODEL
--------------------------------------------------------------------------------
The coding is POSITION-WISE: the value written at command t is a pure function of
cmds[t] alone.  It never looks at another command, at any observation, at the future, or
at any per-sequence state.  Consequences:

  - Prefix-causal, trivially: code_cmds(cmds[:k], z_cmd[:k]) == code_cmds(cmds, z_cmd)[:k].
  - Read-position invariant, trivially: the read command string is the same under the
    native chain and under the role-swapped chain, so its token is bit-identical in both
    arms.  Nothing that distinguishes the two arms can reach the scored position through
    my code.
  - Nothing gated on an observation being present.  The scored position's observation is
    withheld; my mechanism never consults an observation at all, at training or scoring
    time, so it is fully switched on exactly where it is judged.

What the code hands the model is an ADDRESS, i.e. "this command's first argument is the
string X and its destination argument is the string Y", which is already there in the
command string in plaintext.  It does not compute where any content is.  Composing
`mv A B`, `mv B C`, `cat C` into "C holds what A held" is left entirely to the model's
memory: it must learn to read its memory at the source address, write that read value at
the destination address, and query at the read address.  I deliberately did NOT add a
component-wise or prefix-sharing path code: whole-path hashing makes sibling paths
(f385.tmp vs f385.tmp.1) near-orthogonal, which denies the model the lexical stem
shortcut visible in this corpus (destinations are built by suffixing the OTHER content's
original filename), and that shortcut is one that keys on the read location's name and
therefore cancels to exactly zero per window anyway — it can only waste capacity.
I also did not encode any position, index, depth or ordinal, so nothing in the coding
supports a first-mover or chain-position heuristic.

--------------------------------------------------------------------------------
4. THE CROSSOVER: WHAT I KEPT FROM EACH PROGRAM AND WHY
--------------------------------------------------------------------------------
From the PARENT I keep head=r2_dualaddress_move_transport.  It is the only mechanism in
either program that performs a genuine TRANSPORT: it reads the memory at the source key,
writes a gated blend of that read and the step's observation at the destination key, with
one shared path-to-key encoder so a path means the same thing in both roles.  That is
the operation the measurement is about.  The r18 transition memory in the arch cannot do
it — its `_transition_reads` derives ONE key per command and reads and writes at that
same key, so it models "the content at this path changed", never "the content at A is now
at B".  The dual-address head is the piece that moves content, and my stream is what
makes its two extractors separable; before this, both roles were reading the same
superposition.

From the PARTNER I keep three things:
  - arch=r22_retrieval_composition_renderer.  It is a strict superset of the parent's
    r18 arch (it subclasses it) with a zero-initialised, RMS-capped composition renderer
    over the retrieved-content channels, so it IS the parent's arch at initialisation and
    can only add vector-wise interaction between retrieved contents.  Low-risk addition,
    and composing retrieved contents is what a multi-hop board needs.
  - objective=boardpair_swap_difference.  Its first three terms are the parent's
    r12_antiretrieval_ring_negatives verbatim; on top it adds the pair terms that force
    each of two same-trajectory predictions past the midpoint of the two targets along
    their difference direction — the same two-content forced choice the metric makes.
    It is WANTS_CTX, so it receives extract_cmd_input(b), i.e. MY coded command tokens,
    and uses cosine similarity < 0.999 to decide "not the same command".  Under baseline
    coding, two different long paths under the same prefix are far above 0.999 similar
    and the pair miner silently discards them; under my coding identical strings still
    give cosine 1.0 while distinct paths fall to ~0.07 similarity in the coded blocks, so
    the miner recovers the pairs it is meant to find.
  - batcher=r3_cuebalanced_routing_blocks.  It parses mv edges to choose training SAMPLES
    (explicitly legitimate) and drives the first-move-rank and origin-rank marginals
    toward uniform inside hop-count strata.  That directly de-biases the chain-position
    statistic which the brief says cancels only in expectation — it attacks the one
    heuristic that can score positive on the frozen slice without carrying identity.

The three levels line up: the stream provides separable source/destination addresses, the
head transports content between them, and the objective plus batcher force a two-content
forced choice while flattening chain-position cues.

--------------------------------------------------------------------------------
5. WHAT WOULD HAVE TO BE TRUE FOR THIS TO FAIL
--------------------------------------------------------------------------------
  - If the frozen embedding already separated source from destination well enough — i.e.
    if the encoder's contextualisation leaves a large, linearly decodable argument-order
    signal despite mean pooling — then the address coding buys little and the candidate
    reduces to the partner's genome with the parent's head, whose margin over both
    parents could easily be inside run-to-run noise.
  - Overwriting 296 of 768 coordinates deletes real command semantics.  If the surviving
    472 standardized coordinates plus the explicit verb block and form flags are not
    enough for the model's general next-observation prediction, overall fit degrades and
    window eligibility (which is decided by a frozen analytic per-cell table, identically
    for every genome) could interact badly with a worse general model.
  - The model could memorise specific hash patterns from training images instead of
    learning the path-independent operation "match the SRC block of a later command
    against the DST block of an earlier one".  Eval is on held-out IMAGES with paths never
    seen in training, whose codes are fresh pseudo-random vectors; the matching operation
    is path-independent so it should transfer, but a memorising solution would collapse
    on transfer and the score would not move.
  - Address collisions: 128-dim balanced codes give mean |cosine| 0.069 between distinct
    paths, but the arch projects to key_d=64 and the head to key_d=48, where typical
    inter-key |cosine| is set by the projection width rather than by my code.  If that
    projection width is the real bottleneck, a cleaner address changes nothing.
  - I could not run anything: there is no torch in this jail.  Correctness is by
    construction and by the plain-Python checks I did run on the digest permutation, the
    balance/norm/orthogonality of the codes, and the corpus facts in section 1.  I make
    no measured claim about the score.
