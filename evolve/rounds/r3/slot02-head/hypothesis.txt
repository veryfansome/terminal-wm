CANDIDATE: head = r3_occupancy_routed_copy_transport, arch = r22_retrieval_composition_renderer.
Axes changed relative to the parent: head (new impl), arch (taken from the crossover partner). Objective, optim, target, batcher and stream are the parent's, unchanged.

WHAT THE DATA SAYS, because the whole design rests on it. I read evolve/jail_data/train_sample.jsonl (24 sequences, 26-32 steps each). A cups window is: several `cat <path>` exposures, each returning a distinct multi-line body with a canary; then a contiguous block of `mv <src> <dst>` steps; then one `cat <final_path>` test whose output is BYTE-IDENTICAL to the body of one of the exposures. Two facts follow that I checked rather than assumed. (1) Every mutating step's observation is the empty render "cwd=/ exit=0\n" — the move carries no information in its observation at all, only in its command token. Per sequence the empty observation forms one exact-duplicate cluster of 8 to 15 members, while every content that recurs forms an exact-duplicate cluster of exactly 2 or 3. That gap is what my mining thresholds sit in. (2) Because the text is identical, the standardized observation embedding at the test step is exactly equal to the embedding at the exposure step: a move PRESERVES content exactly. The read path in the deep windows is also a near-string-sibling of a DIFFERENT content's resting path (e.g. read `.../sshd_config.cfg.8` while another content still sits at `.../sshd_config.cfg`), which is the name lure the metric is built around.

THE DEFECT I AM FIXING IN THE PARENT'S HEAD. r18_transition_forwardmodel_consistency mines a triple (i, k, j) as "the nearest earlier and nearest later command whose embedding is cosine-similar to command k" and trains f(obs_i, cmd_k) toward obs_j, keeping the triple only when (obs_i - obs_j)^2 is LARGE (change_floor 0.25). In this data the mutating steps are contiguous, so for a move step k the nearest later same-path command j is overwhelmingly another move, whose observation is the empty render — and an empty-vs-content pair passes change_floor with room to spare. So the parent's aux spends most of its weight teaching the arch's shared transition operator to map content to the EMPTY observation, and that operator is applied once per hop inside _transition_reads, so the damage compounds with depth — exactly on the windows the objective scores. That is my explanation for a parent that sits below the unmodified baseline, and it is checkable by reading the two files side by side. I keep the parent's mechanism (mined-triple supervision of the shared transition operator) and invert its target: my triples are pairs of steps whose observations are exact duplicates with a contentless step between them, and the operator is supervised toward CONTENT PRESERVATION, f(obs_at_earlier_duplicate, cmd_at_last_contentless_step) = obs_at_read. That term is in aux_loss under trans_weight and is disabled when the arch exposes no transition_from_emb.

WHAT THE NEW MECHANISM COMPUTES THAT NEITHER PARENT COMPUTES. Both parents route content through an outer-product delta-rule memory (r18 _transition_reads; r2's dual-address transport), which superposes every write into one K-by-D matrix and applies a learned affine edit s*(1+gamma)+beta to the content at every hop. Mine is an explicit slot memory with three properties none of them has.

  (a) COPY, NOT EDIT. Every command position i opens exactly one slot. Its value is V_i = m_i * r_i + (1 - m_i) * obs_i, where r_i is what position i retrieved from earlier slots and m_i is a learned gate over (cmd_i, obs_i). When m_i is 1 the slot stores the retrieved content verbatim — no learned transform stands between the source content and the destination slot, so a five-hop chain applies the identity five times instead of five learned affine maps. Content identity across a chain is exactly what the data does and exactly what the metric measures.

  (b) THE RECURSION IS SOLVED, NOT UNROLLED. r_i = sum_{j<i} att_ij V_j and V_i = m_i r_i + (1-m_i) obs_i together are (I - m*att) V = (1-m)*obs with m*att strictly lower triangular, which the code solves in closed form with one unit-lower-triangular solve. Composition depth is therefore not bounded by the number of transformer layers, by a chunk size, or by any fixed unroll — depth 6 costs the same as depth 1. This is the piece aimed straight at the d4+ half of the eligible slice.

  (c) THE SOURCE OF A MOVE IS FOUND BY OCCUPANCY, NOT BY PARSING POSITION OUT OF A POOLED VECTOR. This is the crux and it is why I did not build a src/dst dual extractor. The command embedding is a mean-pooled sentence vector, so `mv X Y` is close to a blend of X and Y and I do not believe two linear extractors can reliably tell which half is which. I never ask them to. At a move step the query is the single path signature of the whole command; it scores against slots, and only the SOURCE has a slot, because the destination is a fresh name that no earlier command wrote. Occupancy does the disambiguation at run time, from the model's own memory state. That is expressed in code as the log-occupancy bias log(occ_j) added to the scores plus a null column with a learned logit, so a query that matches nothing retrieves ~0 instead of a blur. The destination slot is then the move command's own slot, and it is found later by `cat Y` because the mv command literally contains the whole string Y: a full-path match beats the prefix-only match a name-sibling lure can offer.

  (d) HUBNESS-CORRECTED ADDRESSING (the mechanism imported from outside this problem). All the paths in one window share a long prefix, so all path signatures pile onto one dominant direction and cosine retrieval degenerates — the hubness pathology that all-but-the-top / mean-centering fixes in word- and sentence-embedding retrieval. I subtract, from the QUERY only, sigmoid(center_logit) times the causal running mean of the signatures seen so far in this sequence, then renormalize. Centering the keys by the same per-row mean would cancel inside the softmax, so query-side centering is the complete correction and it costs one cumsum. It is strictly causal (running mean over commands up to and including i; no future command touches the query at i). Its effect is that a slot whose address is generic for this window gets the minimum score for every query, and the discriminative suffix mass — the ".8" that separates the target's chain from the lure — is what survives to decide the match.

WHY THIS SHOULD MOVE comp_ca RATHER THAN SOME OTHER NUMBER. comp_ca is native_hit minus swap_stayed on the same board with the same read token. A predictor keyed on the read location is identical in both arms and scores exactly zero. My head's prediction at the read is the content standing in the slot that the chain of writes deposited there, so re-encoding the move commands to swap two contents' move-position sets changes which slot the query lands on and therefore changes the prediction — the two arms come apart. Nothing in the head resolves a move chain in Python: aux_loss mines only WHICH STEPS to train on (duplicate observations, contentless steps) and its positive target for a mined step is that step's own observation, which is already the main loss's target, so it adds no information the harness was not already supervising. The forward pass sees only frozen embeddings; it never sees a command string, and could not parse a path if it wanted to.

WHAT THE CROSSOVER KEEPS FROM EACH PROGRAM. From the parent: the objective (r22_exact_target_equivalence_quotient — the cups data contains exact-duplicate targets by construction, and quotienting them into one class stops the expose/test pair being pushed apart as a false negative, which the partner's r12 ring objective does not do), the routed-collision-depth batcher (it buckets by hop count, so the deep windows the metric weighs are oversampled), and the transition-consistency aux idea, retargeted as described. From the partner: the r22 composition renderer arch, whose zero-init RMS-capped nonlinear composition over the retrieved-content channels is the piece that lets a retrieved content interact vector-wise with the trunk state instead of only scalar-mixing — which is what a copy-transport read needs on the way into the prediction. The partner's r6 image-blocking batcher is dropped because the parent's batcher already blocks by image inside each bucket.

INITIALISATION AND COST. out_scale is zeros, so the wrapped net's prediction is the unwrapped arch's prediction bit-for-bit at step 0 and the head can only earn its way in. Extra forward cost is dominated by two Linear(768, 128) maps over the ~31 command and ~31 observation positions, roughly a quarter of the arch's own per-step cost by parameter count; the triangular solve and the two attentions are on [B, 31, 31] and are negligible. I could not run the harness from this jail, so that is an arithmetic estimate, not a measurement, and the same goes for every claim above about what the score will do.

WHAT WOULD HAVE TO BE TRUE FOR THIS TO FAIL.
  1. The addressing bet is wrong: if the frozen encoder's pooled embedding of `mv X Y` is not closer, after query centering, to the embedding of `cat Y` than the lure's slot key is, the query lands on the lure and the head routes the wrong content. I cannot test this without the encoder. If it fails, the aux drives out_scale toward zero and the candidate lands near the arch alone.
  2. The mutation gate fails to separate contentless steps: then a move's slot stores a blend containing the empty observation and the leak compounds over hops. The empty render is a single exact vector, so I expect it to be trivially separable, but it is the gate's job, not mine, and it is unverified.
  3. My duplicate/contentless mining is miscalibrated on the real training root. It is calibrated to a measured gap on the sample (content clusters of size 2-3 against an empty cluster of 8-15, threshold max_dup=3 at 5% of the row's mean pairwise distance). If some other pack has many near-identical short contents, they get misread as contentless, the aux mines fewer windows, and the head degrades toward inert rather than harmful.
  4. My reading of the parent's defect is wrong — if the parent's aux was not in fact training the transition operator toward the empty observation, then a large part of the expected gain over the parent evaporates and only the transport head itself is left.
  5. Overwrite semantics: I deliberately do not erase the source slot after a move, on the reasoning that stale slots in a chain hold the same content and are harmless, while erasing does nothing about the competing chain that supplies the lure. If a pack contains paths that are genuinely rewritten with new content, the stale slot competes with the fresh one and retrieval degrades with sequence length.
