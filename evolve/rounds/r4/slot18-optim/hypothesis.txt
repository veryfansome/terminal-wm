WHAT THE CROSSOVER KEEPS FROM EACH PROGRAM

Parent: arch r24_reference_closure_transport + head r20_dualpre_transition_consistency. The closure branch is the only mechanism in either program that resolves a reference chain of arbitrary depth in one pass — C = (I - diag(1-own) A)^{-1} diag(own) OBS, pulled = A C — and r20 is the head co-designed with it, because the pulled content is rendered through net._transition and r20 supervises exactly that shared operator on both a raw-observation pre-state and the arch's own memory pre-state.

Partner: stream r3_srcdst_hashslot_coding. Its arch mechanism is not lost by dropping r22: r22's prefix-content cross-attention computes softmax(q_i . k_j) over strictly earlier observation embeddings, injected at command positions through a zero-init (D,D) readout behind a sigmoid gate. That is exactly the own=1 special case of r24's closure (registers = own*OBS, pulled = A OBS, injected through the zero-init ref_read behind sigmoid(ref_gate)). So r24 already contains r22's channel as its depth-1 term, and the genuinely additive thing the partner has is the stream.

WHY THE STREAM IS THE LOAD-BEARING IMPORT

r24 scores the reference graph from cmd_raw = tok_emb[:, 0::2, :], i.e. the raw command token, through ref_ln -> ref_q / ref_k / ref_p. Under baseline_interleave that token is a mean-pooled sentence embedding of the whole command string, so "does step i's SOURCE path equal step j's DESTINATION path" has to be read out of a single 768-vector in which both operands are already blended. The trajectories in evolve/jail_data/train_sample.jsonl are the case that matters: a cups block cats several files (cups_expose), then issues mv commands whose observation is the empty string ("cwd=/ exit=0\n"), then cats a destination path (cups_test) and gets back the content that was exposed at a different path earlier. Steps 14/19/22 of the first sequence are literally that. Under r3 the command token is the same standardized embedding PLUS a deterministic sparse code that writes the source path into coordinates [0,352), the destination path into [352,704), the verb into [704,752) and seven form flags at [752,759), with a path's k-sparse pattern placed at the SAME relative offsets in whichever block it occupies. A single bilinear form on the raw token can then compute source-of-i against destination-of-j: ref_q selects the source block, ref_k selects the destination block, and q_i . k_j peaks exactly when the two path strings are identical. That match is the edge of the reference graph the closure then transitively resolves.

This is a re-coding of each command from its own string alone. code_cmds sees one command at a time and nothing else - no other step, no observation, no filesystem state - so it hands the model the operands, never the resolution. Composing the operands across steps is still the model's job, and it is the job the score measures.

WHAT THE NEW optim COMPUTES THAT NEITHER PARENT COMPUTES

Both programs run the same optimizer, in which every parameter shares one warmup-hold-cosine-to-floor schedule. The new impl splits the parameters into three timescales instead of two and adds a Polyak-averaged tail.

1. Router group. Two-dimensional weights with shape[1] == D and shape[0] <= router_out_max (128). On this genome that selects exactly ref_q (128,768), ref_k (128,768), ref_p (64,768), ref_keybias (1,768), ref_null (1,768) - the whole reference-closure scorer and nothing else. cmd_proj / obs_proj / read_to_h are (176,768) and fall outside because 176 > 128; ref_own is (1,944); ref_diff is (1,64); ref_gate is (1,179); tr_read and ref_read are (768,768). The parent's Muon selector is untouched and still picks the five bias-free (64,176) addressing extractors (file_read, file_write, path_read, path_write, tr_path) via the same sibling rule, and the spectral cap still picks the two (768,768) readouts. The router group gets lr * router_lr_mult, weight_decay 0, and a schedule that is flat at 1.0 after warmup for the entire run.

2. Constant-step tail plus uniform iterate averaging. The trunk schedule now finishes its cosine at step (steps - window) and sits at floor_ratio for the last avg_frac of the budget, so the tail is a genuine constant-step regime. Over that window the optimizer accumulates a uniform running mean of every parameter (a.lerp_(p, 1/n)) after the update and after the spectral projection, and on the final optimizer step copies the mean into the live parameters and re-projects. Neither parent averages anything; both hand the eval the last iterate.

WHY THIS SHOULD MOVE THE MEASURED QUANTITY

The reference-closure scorer receives literally zero gradient at initialization. ref_read is zero-initialized in both weight and bias, and ref_contrib = sigmoid(ref_gate) * ref_read(chain_render), so d(loss)/d(chain_render) = ref_read.weight^T . d(loss)/d(pred) = 0 at step 0. ref_read.weight itself does get gradient (the outer product of the upstream gradient with chain_render), so the scorer's learning signal ramps in only as ref_read grows away from zero. Under the parent's single schedule that ramp-in overlaps the cosine decay: warmup ends at 4%, the hold ends at 34%, and from there the learning rate falls to 5% of base. The parameters that decide which content is routed where are therefore annealed at the moment their gradient first becomes usable. Holding the scorer at a constant 2x base for the whole run gives it the entire tail to fit, and removing its weight decay stops the 5e-4 decoupled pull that fights the sparse block-selection structure r3 makes available (a selector that keeps only ~48 of 768 input coordinates per output row is exactly the kind of weight that decay erodes).

Running the scorer hot to the last step would leave the final iterate noisy, which is where the averaging earns its place. comp_ca is a mean over ~89 windows of the difference of two argmax indicators, so it is a step function of the weights and a per-window decision is made by a margin; the reported magnitudes (|score| < 0.01) say those margins are near zero, i.e. decisions are being made at the boundary where parameter noise decides them. Polyak-Ruppert averaging of a constant-step trajectory reduces the variance of the final point by ~1/n over the window without touching the bias, and the two known empirical consequences - flatter final point, better transfer - are exactly what a slice held out by IMAGE asks for. The two mechanisms are deliberately paired: the hot router only makes sense because the tail average cleans up after it.

WHAT WOULD HAVE TO BE TRUE FOR THIS TO FAIL

- If the frozen encoder's mean-pooled command embedding already separates source from destination well enough, r3's code adds a large-amplitude (+/-2 per coordinate, 24 nonzeros per path block) perturbation on top of a standardized embedding for no gain, and could displace the embedding geometry the delta-rule addressing already relies on. cmd_proj compresses 768 -> 176 and may partly discard the code; only the closure path sees the raw token at full width, so the benefit is confined to the branch I am arguing for.
- If the closure scorer is not gradient-starved but capacity-starved - if a bilinear form on ref_ln(cmd_raw) simply cannot express the block comparison - then a hotter learning rate on it changes nothing, and the run is a repeat of the parent plus averaging noise.
- If the trained trajectory's tail is not in a single basin (Muon takes fixed-magnitude spectral steps and still follows the trunk schedule here, but the hot router does not settle), the uniform mean of the last 25% of iterates can land between modes and be worse than the last iterate. The window fraction and router_lr_mult are the two knobs that trade this off; 0.25 and 2.0 are chosen conservatively and are unmeasured.
- If the eligible windows are dominated by depth-3 chains that the delta-rule memory already resolves without the closure branch, the closure gate sigmoid(ref_gate) may simply stay low and none of this is reached.
- Speed: the added per-step cost is one lerp_ over the parameter set during the last 25% of steps and one extra full-parameter clone, both negligible against the arch's 32-iteration transition loop. r3's per-command code is cached by command string across the whole run. I have not profiled either on the real budget.
